# Shared nutrition research pipeline (#62)

[Overview](README.md) · [Workflow](workflow.md) · [Assistant contract](assistant-contracts.md#research-request-v1) · [Population playbook](population-playbook.md)

This implementation prepares and reviews ingredient profiles locally. It does not populate or publish the catalog, enable ingredient writes, or add a tracker/recipe research screen. Those consumers remain #63/#66/#69/#70. The optional paid transport is #71; no provider route or paid API transport is implemented here.

## Job schema and lifecycle

A schemaVersion 1 job contains jobId/jobKey, scope/ownerUid, target, requestedFields, parentBatchId/passId, state/version, attempts/checkpoints, match, sourceEvidence, proposal/validation/review, request history and pendingRequest. Compare-and-swap uses version. Packet groups save atomically; validation occurs before any result is staged.

Catalog job keys contain manifest ID; private keys contain namespace, owner and stable identity/variant IDs. Both include sorted requested fields and source release. Public manifest insertion is never required for private input. A parent batch is source-independent; each issued packet records its random requestId, digest and one pass ID in the job store. The pass ID is absent from the packet itself.

States are queued → awaiting_response → needs_review for packets; queued → matched → needs_review for deterministic lookup. Exact curated reuse moves to needs_review with its existing revision so the profile can be reviewed, and it is not fetched again. Approved/imported jobs and matched proposals are never fetched again. Blocked jobs record actionable needs. retryJob explicitly returns a blocked job to queued, clearing its old blocked reason, match, proposal, validation, review, checkpoints, pending request, source evidence and attempt budget so corrected evidence can be matched again. Rejecting a proposal also clears the old match and proposal before the next pass. Expiry/cancel returns awaiting_response jobs to queued; runJob resumes a pending request without fetching, or expires its group when its deadline passes. Reissuing generates a fresh request ID. Already answered, cancelled and expired responses cannot be applied.

The service exposes enqueue, retryJob, runJob/runBatch, prepareRequest, acceptResponse, cancelRequest, attestSource, verifySource, review and report. There is no ingredient-store write call. An approved private job exposes proposal.revisionDraft for a future #61 store caller; INGREDIENT_STORE_WRITES_ENABLED remains false.

## Packet contract and review

Packets contain ingredient identity/forms, requested fields/units, known observations and attempted sources. Meal composition is never selected into a packet. Label evidence is omitted by default; includeLabelEvidence must be explicitly selected, and only text label fields are accepted. Consumers must preview copyableResearchPacket verbatim before copying; the future UI owns that preview.

The canonical body omits requestId, requestDigest and createdAt, sorts targets by targetId and object keys recursively, and preserves other array order. The SHA-256 digest therefore matches between app and CLI; issue IDs use 96 cryptographically random bits. The service partitions jobs by parentBatchId before issuing packets, including CLI packet calls without --batch; each pass ID uses that packet’s own parent batch. Within each batch, mixed sets emit all-field groups first (8 by default), then field-limited groups (25); targets requesting more than 10 fields count as all-field. Byte limits can split groups further or reject an oversized target. Defaults are 200,000 UTF-8 bytes per request, 1,000,000 per response and a seven-day lifetime. PACKET_LIMITS is configurable.

acceptResponse accepts strict JSON only. It validates echoes, pending state, expiry, registry version, profile reference, requested targets/fields, observations, statuses, provenance, units, bounds, URLs and numeric types before building drafts. A null value is valid for unknown, below_quantification_limit, and not_applicable. below_quantification_limit and not_applicable require at least one source id; unknown may omit sources. Those two statuses are not stored as gap reasons. A residual observation that cites no source deletes that field's provenance instead of leaving the base source on the new null. measured, label_reported, calculated, and estimated_from_comparable require a non-null value, in the packet and again in proposal validation. Known observations preserve value (including null), status, qualifier, roundingInterval and upperBound after unit normalization; null is never numerically converted. Store CAS prevents concurrent response replay. Consumers maintaining current library heads should pass currentRefs, keyed by job ID, to acceptResponse; a changed head then rejects a response even if the job record itself has not yet refreshed. Field-limited packet updates and deterministic passes supply target.baseRevision and baseRef. The staged record, field provenance, and sources are seeded from that base before the requested fields are overlaid, so unrequested nutrients and their original source records stay in the new revision. A later pass that cites a different record under the same adapter source key keeps the earlier source instead of replacing its evidence. A first pass with no base still records every unrequested field as unknown with gap:not_requested. Fiber and carbohydrate conventions are part of the staged revision. A first pass copies the normalizer's fiberMeaning total and carbConvention includes_fiber, including an assistant packet that does not say otherwise. A field-limited residual pass keeps the base revision's conventions unless the source explicitly sets new ones. A full-field residual pass uses the normalizer's conventions.

Assistant source verification starts unverified. A proposal with no assistant result is not a deterministic refetch target; verifySource reports that deterministic FDC verification is required instead of failing on a missing result. verifySource compares the full normalized observation for every field cited to that source: value, status, upperBound, roundingInterval, qualifier, and derivation. It also compares every cited conversion, including grams per unit and state and the conversion range. Missing, differently weighted, ambiguously weighted, unexpressed qualified, or differently ranged portions cannot be verified. Any mismatch leaves the source unverified, including after an earlier successful verification, and does not replace the draft. On a match, verifySource writes the deterministic adapter observation onto the draft, including cited nutrient quality, provenance, and conversion ranges, before it hashes the revision. Provenance for each rewritten field points at the source just verified, not at the first id in the citation list. It rebuilds the gap report for those observations. It stores state words for each verified source and checks each source on its own, so a later raw record cannot clear a cooked conflict from an earlier verified source. A raw-only source conflicts with a cooked target even when another verified source is cooked, and a cooked-only source conflicts with a raw target even when another source is raw. A raw record therefore fails a cooked target even when the assistant claimed the cooked state. It then copies the adapter’s source metadata and known license into the draft and its conversions, recalculates the draft hash and conversion IDs, and refreshes validation. A conversion is checked and rewritten when its source list includes the source being verified; the check and the rewrite use that same rule. Approval must use the refreshed review hash. Atwater general factors (nutrient 2047, number 957) and specific factors (nutrient 2048, number 958) retain calculated status and the matching derivation. attestSource records a reviewer for one particular private source and throws for a curated job. Curated approval and staging require every cited source verified by deterministic refetch, not reviewer attestation, and resolved permittedUse metadata. The assistant placeholder review_required blocks curated validation until deterministic refetch copies the adapter’s license. Private approval may instead include reviewer attestation and retains the assistant-researched label. Estimated values retain comparator, transfer reason, derivation and range. Manual and label amounts, upper bounds, rounding intervals, and estimate ranges are converted into registry units, including when a gram serving scales the record to 100 g. Direct adapters reject nutrient keys outside the stored profile. Label state extraction reads productName as well as title, description, and state, so a name such as Cooked Ham or Unsalted Broth can conflict with the target variant. Staged sources need a finite accessedAt, and any publishedAt must be a finite date too. Review is tied to a content hash of the revision draft, every proposed conversion, the gap report, and the published identity (canonical name, aliases, category, kind, and variant dimensions). The review packet lists those conversions, their source evidence, the gaps, the published identity, and the same diff used for approval. For a curated job it also shows each verified FDC record description next to that identity and an identity-mismatch flag. If the match table has an entry for the manifest id, that verified record must equal the entry. Changing a conversion weight, unit, amount, state, source, or range, or changing the gaps, category, kind, or the rest of that identity, after approval invalidates the hash. Staging requires that same hash, re-checks the match table itself (the CLI passes it to stageCatalog), and walks every string and object key on the staged record for email addresses, user or home paths (including Windows paths and file URLs), confidential or restricted text, and blob or data URLs. Packet source ids must be short opaque ids (letters, digits, dot, underscore, hyphen) because they become published source keys. Nutrient qualifiers, provenance derivation and comparatorRef, and source version, datasetId, and originalBasis are included. The word private is not itself a text match. The reviewer must be a handle, not an email address. The word private in a product name is not private data. All warnings must be acknowledged.

## Browser persistence and auth

IndexedDB nutrition-research-jobs-v1 holds one owner's jobs and requests. Same-owner reload resumes pending packets. Opening for another owner clears the database; failure disables access. Sign-out and owner changes clear it through the tracker ingredientSession and Recipe Standardizer auth paths, including explicit sign-out. Clearing invalidates open handles before deletion, with a bounded wait for blocked deletion. No Firebase collection or security rule is added.

Only the research modules imported by tracker auth are added to APP_SHELL; the cache name is nutritrack-v5. Future research UI consumers must register any additional loaded modules when they ship.

## CLI use and safety

Run from the repository root with vite-node (already installed):

```sh
npx --no-install vite-node scripts/nutrition/researchCli.ts -- plan --max 5 --fields protein,iodine
npx --no-install vite-node scripts/nutrition/researchCli.ts -- coverage
```

These commands are dry runs. To persist a local research outbox, explicitly use --write with --store pointing outside public. For example:

```sh
npx --no-install vite-node scripts/nutrition/researchCli.ts -- plan --max 5 --fields protein,iodine --write --store /tmp/nutrition-research
npx --no-install vite-node scripts/nutrition/researchCli.ts -- packet --write --store /tmp/nutrition-research
```

packet prints the request and copyable block. Save the assistant's response as a local JSON file, then use import-packet with --input and the same --store; first omit --write to validate without changing the pending jobs. Add --write only to persist the accepted results. review with --job shows a review packet. Its approval hash covers the revision, every proposed conversion, the gap report, and the published identity, including category and kind. For a curated job, --verify-source <sourceId> refetches that cited FDC source through verifySource. The default adapter is fdc-bulk. --file with a pinned --dataset indexes that bulk file into the source cache first. --source fdc-api selects the live adapter and still requires --live and FDC_API_KEY; without both, the command exits before any request. Curated verification does not use reviewer attestation. attestSource throws for a curated job, and approval or staging accepts only deterministic refetch. review_required is replaced only when the deterministic adapter supplies a license. A private job without --source still uses attestSource with --reviewer. That records reviewer attestation for the named source and leaves review_required unresolved. --decide approve requires --hash, --reviewer and --ack for each warning (separated with a vertical bar); private review may use --attest. The hash is the review content hash from the packet, not the revision hash alone. Corrected values go through a new manual pass. For blocked jobs, retry --job <id> --store <path> previews a queued reset; add --write to persist it, then run or issue a packet again. Retry requires an explicitly selected blocked job and does not fetch sources.

Other commands are index (--dataset/--file), run (--source fdc-bulk, fdc-api, manual or label; manual/label also use --input), validate, stage (--out) and suggest (--manifest-id, optionally --dataset/--file). --batch or --job limits an existing job selection. `run` and `validate` apply the selected jobs one after another, so `--write` can take the store lock for each job in a multi-job batch. `run --input` requires exactly one `--job`, so one manual or label record is not applied to every selected job. `import-packet` still takes `--input` for a response file and does not require `--job`. stage only writes with `--write` and outside public. `stage --write` refuses a non-empty `--out` directory, so a later batch cannot overwrite `manifest.json` and leave earlier shards unlisted. It stages approved jobs and skips the rest; a selection with no approved job is an error. Staging rejects multiple approved passes for the same variant; select one reviewed pass so each variant has one record and profileCount counts unique variants. Suggestion output never edits the reviewed match table. Coverage reports exclude private jobs. For one manifest id, every curated pass is aggregated: the id is approved if any pass is approved, and per-field status is merged across those passes. A later blocked pass does not hide an approved profile.

Every command defaults to dry run. --write requires --store. The file store/source cache use atomic local writes, locks, checksums and CAS. Locks are never stolen automatically by age; after a crash, inspect the recorded PID and remove an abandoned lock explicitly before retrying. Paths resolving through symlinks into public are refused. A malformed cache or store is an error, never an empty successful import. The bulk reader requires a matching SHA-256 pin. A pin with fixtureOnly true accepts only explicitly labeled synthetic fixtures; the two pinned FDC releases below set fixtureOnly false and are accepted only when the file's checksum equals the pin.

There is no network without --live. fdc-api without --live exits nonzero. Its operator-only adapter reads process.env.FDC_API_KEY only after the live gate, sends it in X-Api-Key, and redacts transport/error details. Tests inject fetch and use synthetic keys; no live calls are part of verification. Bulk/manual/label/packet commands need no key. No FDC API key is configured or provisioned; provisioning one under [#62 Part B](../../backlogs/calorie-tracker.md#62-part-b-pin-live-sources-and-publish-staged-curated-data) still needs James's explicit say-so. Catalog import and staged publication proceed as #63 batches with batch reports under his 2026-11-10 standing approval.

### Pinned FDC bulk releases (#62 Part B)

[researchConfig.ts](../../scripts/nutrition/researchConfig.ts) pins two FDC bulk JSON releases, downloaded and checksummed on 2026-11-10 from fdc.nal.usda.gov. Bulk downloads need no key. Each entry records the download URL, the archive checksum (`archiveSha256`), the extracted file name, and the extracted file's checksum (`sha256`). The reader verifies `sha256`, so that field is always the extracted JSON, never the zip.

| Dataset id | Data type | Release | Extracted file | Top-level key |
| --- | --- | --- | --- | --- |
| `foundation` | Foundation | 2026-10-29 (current, October 2026) | FoodData_Central_foundation_food_json_2026-10-29.json | FoundationFoods |
| `sr-legacy` | SR Legacy | 2018-04 (final, April 2018; not updated) | FoodData_Central_sr_legacy_food_json_2018-04.json | SRLegacyFoods |

The reader accepts a top-level array or the FoundationFoods, SRLegacyFoods, BrandedFoods, or foods key. Foundation and SR Legacy are different data types, not independent confirmations of one observation (see the [source hierarchy](population-playbook.md#source-hierarchy)).

The files are operator-local: keep them in a directory outside the checkout (for example `~/fdc-datasets`) and never commit them, zipped or extracted. To re-fetch and verify both layers:

```sh
mkdir -p ~/fdc-datasets && cd ~/fdc-datasets
curl -fLO https://fdc.nal.usda.gov/fdc-datasets/FoodData_Central_foundation_food_json_2026-10-29.zip
curl -fLO https://fdc.nal.usda.gov/fdc-datasets/FoodData_Central_sr_legacy_food_json_2018-04.zip
sha256sum FoodData_Central_*.zip   # compare with archiveSha256 in researchConfig.ts
unzip -o FoodData_Central_foundation_food_json_2026-10-29.zip
unzip -o FoodData_Central_sr_legacy_food_json_2018-04.zip
sha256sum FoodData_Central_*.json  # compare with sha256 in researchConfig.ts
```

If either checksum differs, stop. Do not edit a pin to match a new download; a new release is a new pin in its own reviewed change. With matching files, these dry-run commands verify and index each release in memory without writing anything:

```sh
npx --no-install vite-node scripts/nutrition/researchCli.ts -- index --dataset foundation --file ~/fdc-datasets/FoodData_Central_foundation_food_json_2026-10-29.json
npx --no-install vite-node scripts/nutrition/researchCli.ts -- index --dataset sr-legacy --file ~/fdc-datasets/FoodData_Central_sr_legacy_food_json_2018-04.json
```

The FDC API adapter stays off: the bulk path does not use it, and no API key is configured anywhere.

### Priority-1 dry-run pilot (#76)

### Flat-food conversion analysis (#77)

`npx --no-install vite-node scripts/nutrition/conversionAnalysisCli.ts -- --extract <path>` checks whether each flat v1 saved food in a foods-only extract converts to a direct v2 profile without loss.
