# Shared nutrition research pipeline (#62)

[Overview](README.md) · [Workflow](workflow.md) · [Assistant contract](assistant-contracts.md#research-request-v1) · [Population playbook](population-playbook.md)

This implementation prepares and reviews ingredient profiles locally. It does not populate or publish the catalog, enable ingredient writes, or add a tracker/recipe research screen. Those consumers remain #63/#66/#69/#70. The optional paid transport is #71; no provider route or paid API transport is implemented here.

## Job schema and lifecycle

A schemaVersion 1 job contains jobId/jobKey, scope/ownerUid, target, requestedFields, parentBatchId/passId, state/version, attempts/checkpoints, match, sourceEvidence, proposal/validation/review, request history and pendingRequest. Compare-and-swap uses version. Packet groups save atomically; validation occurs before any result is staged.

Catalog job keys contain manifest ID; private keys contain namespace, owner and stable identity/variant IDs. Both include sorted requested fields and source release. Public manifest insertion is never required for private input. A parent batch is source-independent; each issued packet records its random requestId, digest and one pass ID in the job store. The pass ID is absent from the packet itself.

States are queued → awaiting_response → needs_review for packets; queued → matched → needs_review for deterministic lookup. Exact curated reuse stays matched with its existing revision. Approved/imported jobs and matched proposals are never fetched again. Blocked jobs record actionable needs. retryJob explicitly returns a blocked job to queued, clearing its old blocked reason, match, proposal, validation, review, checkpoints, pending request, source evidence and attempt budget so corrected evidence can be matched again. Rejecting a proposal also clears the old match and proposal before the next pass. Expiry/cancel returns awaiting_response jobs to queued; runJob resumes a pending request without fetching, or expires its group when its deadline passes. Reissuing generates a fresh request ID. Already answered, cancelled and expired responses cannot be applied.

The service exposes enqueue, retryJob, runJob/runBatch, prepareRequest, acceptResponse, cancelRequest, attestSource, verifySource, review and report. There is no ingredient-store write call. An approved private job exposes proposal.revisionDraft for a future #61 store caller; INGREDIENT_STORE_WRITES_ENABLED remains false.

## Packet contract and review

Packets contain ingredient identity/forms, requested fields/units, known observations and attempted sources. Meal composition is never selected into a packet. Label evidence is omitted by default; includeLabelEvidence must be explicitly selected, and only text label fields are accepted. Consumers must preview copyableResearchPacket verbatim before copying; the future UI owns that preview.

The canonical body omits requestId, requestDigest and createdAt, sorts targets by targetId and object keys recursively, and preserves other array order. The SHA-256 digest therefore matches between app and CLI; issue IDs use 96 cryptographically random bits. The service partitions jobs by parentBatchId before issuing packets, including CLI packet calls without --batch; each pass ID uses that packet’s own parent batch. Within each batch, mixed sets emit all-field groups first (8 by default), then field-limited groups (25); targets requesting more than 10 fields count as all-field. Byte limits can split groups further or reject an oversized target. Defaults are 200,000 UTF-8 bytes per request, 1,000,000 per response and a seven-day lifetime. PACKET_LIMITS is configurable.

acceptResponse accepts strict JSON only. It validates echoes, pending state, expiry, registry version, profile reference, requested targets/fields, observations, statuses, provenance, units, bounds, URLs and numeric types before building drafts. A null value is valid for unknown, below_quantification_limit, and not_applicable. measured, label_reported, calculated, and estimated_from_comparable require a non-null value, in the packet and again in proposal validation. Known observations preserve value (including null), status, qualifier, roundingInterval and upperBound after unit normalization; null is never numerically converted. Store CAS prevents concurrent response replay. Consumers maintaining current library heads should pass currentRefs, keyed by job ID, to acceptResponse; a changed head then rejects a response even if the job record itself has not yet refreshed. Field-limited packet updates and deterministic passes supply target.baseRevision and baseRef. The staged record, field provenance, and sources are seeded from that base before the requested fields are overlaid, so unrequested nutrients and their original source records stay in the new revision. A later pass that cites a different record under the same adapter source key keeps the earlier source instead of replacing its evidence. A first pass with no base still records every unrequested field as unknown with gap:not_requested. Fiber and carbohydrate conventions are part of the staged revision. A first pass copies the normalizer's fiberMeaning total and carbConvention includes_fiber, including an assistant packet that does not say otherwise. A field-limited residual pass keeps the base revision's conventions unless the source explicitly sets new ones. A full-field residual pass uses the normalizer's conventions.

Assistant source verification starts unverified. verifySource compares the full normalized observation for every field cited to that source: value, status, upperBound, roundingInterval, qualifier, and derivation. It also compares every cited conversion, including grams per unit and state and the conversion range. Missing, differently weighted, ambiguously weighted, unexpressed qualified, or differently ranged portions cannot be verified. Any mismatch leaves the source unverified, including after an earlier successful verification, and does not replace the draft. On a match, verifySource writes the deterministic adapter observation onto the draft, including cited nutrient quality, provenance, and conversion ranges, before it hashes the revision. It rebuilds the gap report for those observations, and it replaces extracted state words with the words from the deterministic record before re-validation. A raw record therefore fails a cooked target even when the assistant claimed the cooked state. It then copies the adapter’s source metadata and known license into the draft and its conversions, recalculates the draft hash and conversion IDs, and refreshes validation. A conversion is checked and rewritten when its source list includes the source being verified; the check and the rewrite use that same rule. Approval must use the refreshed review hash. Atwater general factors (nutrient 2047, number 957) and specific factors (nutrient 2048, number 958) retain calculated status and the matching derivation. attestSource records a reviewer for one particular source. Curated approval and staging require every cited source verified and resolved permittedUse metadata. The assistant placeholder review_required blocks curated validation even after reviewer source attestation; deterministic refetch can resolve it from the adapter’s license. Private approval may instead include reviewer attestation and retains the assistant-researched label. Estimated values retain comparator, transfer reason, derivation and range. Manual and label amounts, upper bounds, rounding intervals, and estimate ranges are converted into registry units, including when a gram serving scales the record to 100 g. Direct adapters reject nutrient keys outside the stored profile. Label state extraction reads productName as well as title, description, and state, so a name such as Cooked Ham or Unsalted Broth can conflict with the target variant. Staged sources need a finite accessedAt, and any publishedAt must be a finite date too. Review is tied to a content hash of the revision draft, every proposed conversion, the gap report, and the published identity (canonical name, aliases, category, kind, and variant dimensions). The review packet lists those conversions, their source evidence, the gaps, the published identity, and the same diff used for approval. Changing a conversion weight, unit, amount, state, source, or range, or changing the gaps, category, kind, or the rest of that identity, after approval invalidates the hash. Staging requires that same hash and scans the full staged record for private data, including gap text and identity. All warnings must be acknowledged.

## Browser persistence and auth

IndexedDB nutrition-research-jobs-v1 holds one owner's jobs and requests. Same-owner reload resumes pending packets. Opening for another owner clears the database; failure disables access. Sign-out and owner changes clear it through the tracker ingredientSession and Recipe Standardizer auth paths, including explicit sign-out. Clearing invalidates open handles before deletion, with a bounded wait for blocked deletion. No Firebase collection or security rule is added.

Only the research modules imported by tracker auth are added to APP_SHELL; the cache name is nutritrack-v5. Future research UI consumers must register any additional loaded modules when they ship.

## CLI use and safety

Run from the repository root with vite-node (already installed):

```sh
npx --no-install vite-node scripts/nutrition/researchCli.ts -- plan --max 5 --fields protein,iodine
npx --no-install vite-node scripts/nutrition/researchCli.ts -- coverage
```

These commands are dry runs. To persist a local research outbox, explicitly use --write with --store pointing outside public. For example:

```sh
npx --no-install vite-node scripts/nutrition/researchCli.ts -- plan --max 5 --fields protein,iodine --write --store /tmp/nutrition-research
npx --no-install vite-node scripts/nutrition/researchCli.ts -- packet --write --store /tmp/nutrition-research
```

packet prints the request and copyable block. Save the assistant's response as a local JSON file, then use import-packet with --input and the same --store; first omit --write to validate without changing the pending jobs. Add --write only to persist the accepted results. review with --job shows a review packet. Its approval hash covers the revision, every proposed conversion, the gap report, and the published identity, including category and kind. For a curated job, --verify-source <sourceId> refetches that cited FDC source through verifySource. The default adapter is fdc-bulk. --file with a pinned --dataset indexes that bulk file into the source cache first. --source fdc-api selects the live adapter and still requires --live and FDC_API_KEY; without both, the command exits before any request. Curated verification does not use reviewer attestation, so review_required is replaced only when the deterministic adapter supplies a license. A private job without --source still uses attestSource with --reviewer. That records reviewer attestation for the named source and leaves review_required unresolved. --decide approve requires --hash, --reviewer and --ack for each warning (separated with a vertical bar); private review may use --attest. The hash is the review content hash from the packet, not the revision hash alone. Corrected values go through a new manual pass. For blocked jobs, retry --job <id> --store <path> previews a queued reset; add --write to persist it, then run or issue a packet again. Retry requires an explicitly selected blocked job and does not fetch sources.

Other commands are index (--dataset/--file), run (--source fdc-bulk, fdc-api, manual or label; manual/label also use --input), validate, stage (--out) and suggest (--manifest-id, optionally --dataset/--file). --batch or --job limits an existing job selection. `run` and `validate` apply the selected jobs one after another, so `--write` can take the store lock for each job in a multi-job batch. `run --input` requires exactly one `--job`, so one manual or label record is not applied to every selected job. `import-packet` still takes `--input` for a response file and does not require `--job`. stage only writes with `--write` and outside public. It stages approved jobs and skips the rest; a selection with no approved job is an error. Staging rejects multiple approved passes for the same variant; select one reviewed pass so each variant has one record and profileCount counts unique variants. Suggestion output never edits the reviewed match table. Coverage reports exclude private jobs. For one manifest id, every curated pass is aggregated: the id is approved if any pass is approved, and per-field status is merged across those passes. A later blocked pass does not hide an approved profile.

Every command defaults to dry run. --write requires --store. The file store/source cache use atomic local writes, locks, checksums and CAS. Locks are never stolen automatically by age; after a crash, inspect the recorded PID and remove an abandoned lock explicitly before retrying. Paths resolving through symlinks into public are refused. A malformed cache or store is an error, never an empty successful import. The bulk reader requires a matching SHA-256 pin and currently permits only explicitly labeled synthetic fixtures. Production pins are deliberately absent.

There is no network without --live. fdc-api without --live exits nonzero. Its operator-only adapter reads process.env.FDC_API_KEY only after the live gate, sends it in X-Api-Key, and redacts transport/error details. Tests inject fetch and use synthetic keys; no live calls are part of verification. Bulk/manual/label/packet commands need no key. Live credentials and access are dependencies of [#62 Part B](../../backlogs/calorie-tracker.md#62-part-b-pin-live-sources-and-publish-staged-curated-data), requiring James's explicit approval. Publishing catalog shards and #63 population remain separately approval-gated.
